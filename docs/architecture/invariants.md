# Invariants

Rules that must always hold. **Each one says how it is enforced and how that
enforcement is shown to work.** A rule with neither is a wish, not an invariant.

Identity, membership, channel and message invariants are implemented below.
Row security is enabled and forced on every application table.
The **Lands in** column says whether a rule is already in place or which issue
brings it; until then it is the contract that issue is implemented against.

## How invariants are enforced, in order of preference

1. **A constraint** — `NOT NULL`, `CHECK`, `FOREIGN KEY`, `UNIQUE`. Holds even if
   the code forgets
2. **A privilege** — `GRANT`, `REVOKE`, row security. Holds even if the code is
   wrong
3. **One place in code, serialised by a row lock** — only when neither of the
   above can express the rule, and the reason is written down

A test **breaks each invariant and watches it be refused.** A test that only shows
the happy path says nothing about whether the guard exists.

In the *Enforced by* column, **Review** is the formal notation for enforcement
that still depends on people. It is debt, not a mechanism: the same cell must
cite the issue that will replace it and name the planned mechanism.
`crates/app/tests/invariants_document.rs` checks every table with an *Enforced by*
column for the word "review" anywhere in that cell, ignoring case, and requires
an issue citation (`#<number>`). It also rejects mismatched cell counts and a
document with no invariant tables or rows.

**Accepted gap:** the test checks only the written citation. It does not check
whether the issue exists, is open, or concerns that rule; a mistyped, unrelated
or closed issue passes. It makes no GitHub API calls and does not judge the
strength of mechanisms in other rows.

## Columns

| Invariant | Enforced by | Lands in |
|---|---|---|
| **Every column is `NOT NULL` unless it is named nullable, with a reason** | NULL gets past every other constraint on a column: **a `CHECK` passes on NULL, a `UNIQUE` admits any number of NULLs (unless declared `NULLS NOT DISTINCT`), a foreign key with the default `MATCH SIMPLE` requires no match when a referencing column is NULL, and a `DEFAULT` applies only when the column is omitted** — an explicit NULL is stored. So `NOT NULL` is the rule and nullability is the exception: the issue that adds a nullable column names it and says why, and **a schema test holds that list and fails on any other nullable column** | in place |
| **Each enumerated value has one spelling in production Rust, and the database's `CHECK` admits exactly those values. SQL text and test fixtures and expectations are not covered** | `enumeration!` generates `as_str()`, `parse` and all variants from one list; a test compares their names with the column `CHECK`s. For `ChannelScope`, it compares `as_str()` with the scope literals in the table `CHECK` | in place |
| **A row's identity, owner and parent never change** — no row moves to another organization, actor, parent or target, or changes its kind | **`UPDATE` is granted only on the columns the issue that adds them names as updatable, with a reason — never on a table.** Every other column stays read-only, so the rule covers columns nobody thought of: ids, `organization_id`, `actor_id`, parent and target keys such as `team_id`, `channel_id` and `target_team_id`, `actors.type`, `invites.kind`, `token_hash`. **A row in another place is a new row.** The exact-privileges test holds the list | in place |
| **A foreign key to rows the application can delete leads an index** | PostgreSQL does not index the referencing columns of a foreign key, so without one every delete scans the referencing table. **The rule is scoped to deletable rows** — those `fukulow_app` holds `DELETE` on, and those a cascade from them reaches — because most referenced tables here are never deleted from, and an index on those keys would cost every insert and serve no delete. A lookup on a foreign key column is an ordinary query and is indexed when a plan shows it needs to be. A schema test fails on any such key whose columns do not lead a valid, non-partial index | in place |

### At least one owner

Not expressible as a constraint: "at least one row" is neither a `CHECK` nor a
`UNIQUE`.

**It cannot be held without a lock.** Two administrators demote the two remaining
owners at the same moment; each counts two owners, each is allowed, both commit,
and there are none. So every change to `role` or `status` — in `db`, which owns
transactions — begins with:

```sql
SELECT 1 FROM organizations WHERE id = $1 FOR UPDATE;
```

Leaving first locks its actor `FOR UPDATE`, then, in `ORDER BY id` order, **the
organizations where it is an active member** — the only ones the owner rule can apply to;
an inactive membership's organization is not visible to it under row security. **A role
change on an inactive membership is still serialised with the departure**: the departure
writes its audit record into that organization before changing the membership's status,
and that insert's foreign key takes `FOR KEY SHARE` on the organization, which conflicts
with `change_member_role`'s `FOR UPDATE`. The role change therefore reads the membership
only after the departure commits, and finds it `left`. A concurrency test pins this, and
fails if `change_member_role` stops locking the organization. Every membership addition or reactivation first locks the
actor `FOR SHARE` and refuses a non-null `deleted_at`; the actor lock always
precedes organization locks. Audit inserts also take a foreign-key lock on the
performer's actor, so mutations lock that actor before the organization too;
multiple actor locks use `ORDER BY id`. This prevents a new membership from committing after
a departure has enumerated the actor's organizations.

Changes to one organization's owners then happen one at a time, and a count stays
true until the write that depends on it. **The rule itself — whether this change
would leave no active owner — is a pure function in `domain`**, given the current
owners and the proposed change. `db` takes the lock, reads the owners, asks
`domain`, and writes or refuses.

Owners may be several. **The last active owner cannot be demoted, suspended or
leave.** Creating an organization and making its creator the owner is one
transaction.

**Tested by running two demotions genuinely concurrently.** A sequential test
cannot exercise the interleaving that breaks this.

## Invites

| Invariant | Enforced by | Lands in |
|---|---|---|
| Every invite has a kind, and there is no default | `NOT NULL`, no `DEFAULT` | in place |
| Every invite expires | `expires_at NOT NULL` | in place |
| A token is never stored | Only `token_hash` exists | in place |
| A token hash identifies at most one invite, and at most one session | `UNIQUE` on `invites.token_hash` and `sessions.token_hash` — the index a lookup by token uses | in place |
| **An invite is never used more times than allowed** | One conditional statement decides and increments together; `CHECK (used_count <= max_uses)`, `CHECK (used_count >= 0)` and `CHECK (max_uses > 0)` as a backstop | in place |
| **An invite token never appears in a URL the server receives** | Links use the configured public origin and `/invite#<token>`; acceptance reads the token from the JSON body. Router tests pin the three versioned routes and refuse path or query credentials | in place |

```sql
UPDATE invites
   SET used_count = used_count + 1
 WHERE token_hash = $1
   AND used_count < max_uses
   AND revoked_at IS NULL
   AND expires_at > now()
RETURNING ...;
```

Zero rows means refused. **Reading `used_count` and deciding in code lets two
people both see "one use left".** Tested by accepting an invite with
`max_uses = 1` from many concurrent requests and admitting exactly one person.

## Messages

| Invariant | Enforced by | Lands in |
|---|---|---|
| Within a channel, `channel_seq` has no gap and no duplicate | The number is taken with `UPDATE channels SET next_message_seq = next_message_seq + 1 ... RETURNING`, which locks the channel row, **and the message is inserted in the same transaction** — if the insert fails, the increment rolls back with it. Plus `UNIQUE (channel_id, channel_seq)`. A test forces an insert to fail and shows the next message receives the number the failed one would have had | in place |
| **Ordering and cursors use `channel_seq`, never a message id** | Contract | #6 |
| A repeated client-generated message id does not create a second message | `PRIMARY KEY (id)`; the insert and counter roll back on conflict before a separate read-only transaction matches id, organization, channel and sender. Only that match returns the stored message; a match on id alone is a conflict that reveals nothing | in place |

**Why not the message id, or a global sequence.** A client-generated id is ordered
by the client's clock, which can be wrong. More fundamentally, **the order in which
values are handed out is not the order in which transactions commit** — true of a
global `bigserial` too. A reader can move its cursor past a row that has not become
visible yet and never see it. A per-channel counter taken under the channel's row
lock makes the two orders the same.

## Audit

| Invariant | Enforced by | Lands in |
|---|---|---|
| **Audit records are never changed or removed** | The application role holds no `UPDATE` or `DELETE` on `audit_events`. Tested **connected as that role** | in place |
| A change of state and its audit record commit together | The same transaction | in place |
| **Every audit record names the actor who did it** | `audit_events.actor_id NOT NULL`, referencing `actors`. The system is an actor type, so "the system did it" needs no NULL and no special column | in place |
| **Audit metadata never holds a secret or personal data** — no token, password, email address or name | Metadata is built by a typed function per action whose parameters are ids and enumerations; callers cannot pass arbitrary JSON or free text. **This is not only tidiness: audit records can never be updated or deleted, so personal data written there could never be erased when someone leaves the service** | in place |

**A change of name is audited by who changed whose name, and when — not by the old
and new values.** Recording the values would put a display-name snapshot into the
one table that can never be erased.

## Privileges and row security

| Invariant | Enforced by | Lands in |
|---|---|---|
| **The application does not own its tables** | Separate `fukulow_migrator` and `fukulow_app` roles. An owner bypasses row security | in place |
| **The server never runs migrations and never holds the migrator's credentials; migrations run in a separate one-shot process** | `fukulow migrate` is the only production path that reads `MIGRATOR_DATABASE_URL` or calls `db::migrate`, and only `db` embeds the migrations: a source test in `crates/app/tests/source_rules.rs` pins those sites, and refuses renaming the `db` crate or an environment reader (`use std::env::var as …`), which would hide a call from it. In `compose.yaml`, the one-shot `migrate` service has only the migrator's URL and password, `app` has only its own and starts after `migrate` completes successfully, and the administrator password reaches `postgres` alone | in place |
| **The application role cannot bypass row security** | `fukulow_app` is not the table owner, not a superuser, and has no `BYPASSRLS`. No role is ever created with `BYPASSRLS`. **A superuser always bypasses row security**, and an owner does unless `FORCE` is set — which is why the application connects as neither | in place |
| The application holds exactly the privileges it needs, and no more | Granted table by table, and `UPDATE` column by column; **no `ALTER DEFAULT PRIVILEGES`**. A row lock (`FOR UPDATE` or `FOR SHARE`) needs `UPDATE` on at least one column: `actors.display_name` and `organizations.name` provide it. A test compares actual privileges **on every table and every column** against the expected set. **Checking tables alone misses a column grant:** `has_table_privilege(..., 'UPDATE')` is false for a role holding `UPDATE` on one column | in place |
| Every tenant-owned, cross-tenant and global table has row security enabled and forced | `ENABLE` and `FORCE ROW LEVEL SECURITY`. A test enumerates all application tables and fails if any lacks a policy, `relrowsecurity` or `relforcerowsecurity`. `_sqlx_migrations` is internal and has no application privilege | in place |
| **A query with no identity or credential set sees no row** | One populated test per readable table, including globals. `actors` admits self and every actor with a membership, of any status, in an organization where the acting actor is active; `users` admits self or the presented sign-in email (ASCII case-insensitive); `sessions` admits self or the presented token hash. `invites` also admits the presented invite hash. Credential tests pin one matching row and zero for a wrong value. `audit_events` and `_sqlx_migrations` deny reads entirely | in place |
| **Identity never leaks between requests** | `set_config(..., true)` inside the transaction, never session-level `SET`: `fukulow.actor_id`, `fukulow.session_token_hash`, `fukulow.sign_in_email`, `fukulow.invite_token_hash`. One `db::begin` sets the context; source tests pin that boundary. Transactions on one pooled connection prove each of the four contexts sets only its own setting and disappears after commit and rollback | in place |
| Row security is a last wall, not the only one | Repository code still filters tenant-owned data by `organization_id`; `organizations` uses its own `id`. Capabilities decide whether an operation is permitted; a visible row grants no capability | in place |
| **Row security admits only active members to ordinary organization data — not yet members from outside it** | Membership-derived policies. Inactive actors can read and remove their own listings and record their own departure, but see nobody else's rows; their organization membership may only become `left` with no display name, and a trigger forbids changing its role. An outside actor's channel listing grants no message access and cannot be added through the application; **leaving the service still removes it and records `channel.member.removed` in the channel's organization**, admitted only while the actor's own listing names that channel and organization, and written before the listing is deleted. Tests pin this closed gap until connections are built (#43) | in place |
| **Row-security settings carry what the request presented — an actor, a token hash, an email address — never an organization** | The four `db::Context` variants; public `db::TokenHash` accepts exactly 64 lowercase hexadecimal characters and never hashes. The invite transaction sets the newly created actor before its `users` insert. The invite membership policy requires an active member for the acting actor in the invite's organization, and an unrevoked, unexpired organization invite whose `xmin` is the current transaction. A trigger requires a bounded `used_count + 1` for any new unrevoked row version; initial counts must be zero. A no-op UPDATE cannot manufacture the proof | in place |
| **Exactly two `SECURITY DEFINER` functions read memberships unfiltered** | `fukulow_active_organizations()` and `fukulow_organization_has_members(uuid)`, owned by `fukulow_migrator`, with `search_path = pg_catalog, pg_temp`, schema-qualified tables and no `PUBLIC EXECUTE`. Only membership SELECT admits the owner under FORCE. `fukulow_active_organizations()` is `PARALLEL RESTRICTED` so `messages_select` keeps a parallel scan: its array InitPlan runs in the leader above Gather; other policies retain `IN (SELECT ...)`. Tests enumerate the exact functions and parallel labels, repeat the temporary-table attack, and assert the count plan's InitPlan and parallel scan | in place |
| **A migration that touches tenant rows states how it handles row security; `FORCE` is never left off** | Data migrations bracket tenant reads and writes with `NO FORCE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY` in their own transaction, so failure rolls back the exemption. **Review** flags missing handling or restoration (#59: a check that data migrations bracket tenant reads and writes with row-security handling); the schema test rejects a table left without FORCE. No standing bypass | in place |

**Why no `ALTER DEFAULT PRIVILEGES`.** It would hand the application `UPDATE` and
`DELETE` on every new table, including `audit_events`, and depend on someone
remembering to take them back. **A missing `GRANT` fails loudly the first time the
code runs. A missing `REVOKE` fails silently forever.**

**Why no operation without an identity.** Row security admits nothing without an
actor or a presented credential. A background job would see no rows and quietly do nothing — or tempt someone
to add a bypass. So there are none: expiry is decided when reading
(`expires_at > now()`), and nothing needs to sweep. A job added later must run in
one organization's context at a time, as an actor that is a member of it.
